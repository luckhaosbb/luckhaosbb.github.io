// ESTUDO DE CASO DE ARQUITETURA — MARKETPLACE & CONCORRÊNCIA ATÔMICA

HomeWash — Intermediação Sob Demanda &
Concorrência Atômica Sem Distributed Locks

Plataforma web de intermediação de lavagem automotiva a domicílio em operação piloto em Fortaleza (Aldeota, Meireles e Papicu). Arquitetada sob Clean Architecture e TypeScript 5.9 end-to-end, implementa a regra "o primeiro que aceita leva" com resolução atômica no MongoDB, contrato OpenAPI verificado no CI e segurança estrita de cookies host-only.

// 01. MODELO DE NEGÓCIO & PILOTO

O Desafio do Aceite Exclusivo sob Demanda

Regra Central: "Primeiro que Aceita Leva"

Ao contrário de marketplaces tradicionais de cotação lenta, o HomeWash foi desenhado para eliminar a fricção de escolha e negociação:

  • Preço Tabelado e Imutável: O cliente escolhe o serviço e o veículo pelo valor fixado pela plataforma, sem necessidade de comparar propostas individuais.
  • Mural Georreferenciado: Lavadores aprovados que atendem bairros específicos de Fortaleza visualizam solicitações pendentes instantaneamente.
  • Aceite Único e Exclusivo (F8): O primeiro prestador que confirma o atendimento ganha o pedido. Nenhum outro prestador pode assumi-lo concorrentemente.

Disciplina UNIFOR & Escopo do Piloto

Projeto desenvolvido na disciplina Projeto Aplicado em Desenvolvimento de Software na Universidade de Fortaleza (UNIFOR), sob rigorosa governança de engenharia:

  • Delimitação Territorial: Piloto em 3 bairros contíguos de Fortaleza (Aldeota, Meireles e Papicu).
  • Sem Servidor de Aplicação Pesado: Substituição de topologias pesadas (Java EE / WildFly) por processos Node.js conteinerizados ultraleves.
  • Design System Modernist: Interface orientada a tokens semânticos, responsiva de 360px a 1440px sem aplicativos nativos desnecessários.
O Desafio da Concorrência Real

Em um modelo de alta disputa onde múltiplos lavadores olham o mesmo mural simultaneamente, o risco de dois prestadores clicarem em "Aceitar" na mesma fração de segundo é real. A integridade do sistema não podia depender de travas na interface (que são facilmente burladas via requisições diretas à API) nem de locks de memória locais (que falham caso a aplicação escale horizontalmente).

// 02. PADRÃO DE CONCORRÊNCIA

Resolução Atômica no MongoDB sem Distributed Locks

Em vez de introduzir uma camada extra de infraestrutura com Redis e o algoritmo Redlock para gerenciar locks distribuídos de curta duração, a arquitetura do HomeWash aproveitou a semântica de documento único do MongoDB:

// Operação atômica condicional no nível do storage engine do MongoDB // Se 10 prestadores enviarem o POST simultaneamente, exatamente 1 obterá o documento atualizado const resultado = await SolicitacaoModel.findOneAndUpdate( { _id: solicitacaoId, status: 'CRIADO' // Precondição atômica: só aceita se o status atual ainda for CRIADO }, { $set: { status: 'ACEITO', prestadorId: prestadorLogadoId, aceitoEm: new Date() } }, { new: true } ); if (!resultado) { // Retorno 409 Conflict: O pedido já foi aceito por outro profissional milissegundos antes throw new ConflictError('Esta solicitação já foi aceita por outro prestador.'); }
Sem Transações Distribuídas (2PC)
ACID ao Nível de Documento

No MongoDB, a escrita sobre um documento único é inerentemente atômica e serializada pelo WiredTiger. Nenhuma transação multi-documento é necessária.

Agregado Completo em 1 Leitura
Domínio Orientado a Documentos

Uma solicitação carrega o tipo de serviço, o endereço e o veículo encapsulados. Ela é lida inteira e nunca em pedaços fragmentados.

// 04. DECISÕES ESTRUTURAIS & ADRs

Architectural Decision Records (ADRs)

ADR-01 APROVADO & IMPLEMENTADO

TypeScript 5.9 Estrito em Ambos os Aplicativos

Critério da Decisão: Uma linguagem única para front e back elimina troca de contexto em uma equipe de cinco pessoas com prazo estrito de quatro meses. Os tipos do contrato da API são gerados a partir do OpenAPI e consumidos pelo front; quebras de contrato falham na compilação, nunca em produção.
ADR-02 APROVADO & IMPLEMENTADO

Express 5 + exjs-controllers vs. Frameworks Pesados

Critério da Decisão: O framework entrega controllers decorados, injeção de dependência e validação Zod sem impor servidores Java EE ou WildFly pesados. O servidor de aplicação é o próprio processo Node conteinerizado.
ADR-03 APROVADO & IMPLEMENTADO

Sessão JWT com Cookie Host-Only e Sem Domain Wildcard

Critério da Decisão: O cookie homewash_sessao é configurado como httpOnly (inviolável a XSS), Secure e SameSite=Lax. A ausência intencional do atributo Domain impede que o cookie seja compartilhado com outros subdomínios da infraestrutura Dokploy na VPS.
ADR-04 APROVADO & IMPLEMENTADO

Build Reprodutível no GitHub Actions (GHCR) & Dokploy

Critério da Decisão: O GitHub Actions compila as imagens Docker e as publica no GHCR; nada é compilado na VPS de produção. A tag :sha-<commit> assegura rollback imutável e auditável com zero consumo de recursos na VPS durante o deploy.
